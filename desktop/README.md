# desktop — DSH Trading desktop app

English | [中文](README.zh.md)

An Electron shell that turns the dsh-trading Web GUI into an installable desktop app for macOS and Windows. The installer bundles a complete toolchain — a standalone Node.js runtime with npm and pnpm (the version pinned by the repository's `packageManager`), the dsh host, and a preinstalled trading-web profile (official web surface plus the base and crypto/us/cn/hk market bundles, packed from this repository's own packages) — so the app runs with zero preinstalled tooling on a machine that has never seen a development environment.

## What it does

- Double-click launch: the app seeds `~/.dsh-trading/profiles/trading-web` from the bundled profile when it is missing, starts the dsh host on a free loopback port with the bundled Node runtime (`dsh --profile trading-web --no-open`), waits for the GUI, and loads the tokenized URL the host prints (the auth fence issues a per-process token; the resulting session cookie lives in the app window).
- Custom installation wizard: Windows NSIS installer provides a multi-step setup wizard with custom destination directory selection (silent one-click mode disabled).
- Silent VC++ redistributable integration: Bundles Microsoft Visual C++ 2015-2022 Redistributable (x64), automatically checks 64-bit Windows registry during install, and installs silently if missing, preventing host startup crashes (0xC0000135) on clean Windows setups.
- Uninstallation prompt: Asks the user via interactive dialog whether to clean the `~/.dsh-trading` data directory and local caches upon uninstall (the shared `~/.dsh` home of the dsh web host is never touched).
- Handoff instead of double hosts: when a dsh web GUI already answers at `http://127.0.0.1:3080`, the app opens that URL in the system browser (whose cookie jar already holds the session) and quits. Two web hosts on one `~/.dsh` are never started.
- Shares `~/.dsh` with any existing dsh installation: profiles the app seeded itself carry a `.dsh-desktop-seed.json` marker and are re-seeded when the bundled runtime changes; profiles without the marker are user-managed and never touched. The user's `cordis.patch.yml` layer survives re-seeding.
- Trading safety semantics are unchanged: orders default to dry-run behind the base approval gate exactly as in the CLI (`liveTrading` stays an explicit opt-in).
- One window per machine: a second launch focuses the existing window. Closing the window quits the app and gracefully stops the host it spawned (process-group SIGTERM, `taskkill /T` on Windows, forced after 5s).
- Startup failures land on an error page with precise exit diagnostics (including VC++ missing guidance and download button) and the host log tail, a Retry button, and a Reveal-log-file button. The full host log lives at the Electron `logs` directory (`dsh-host.log`).

## Repository layout

| Path | Content |
| --- | --- |
| `src/` | Electron main process (`main.cjs`), testable pure helpers (`runtime.cjs`), preload, splash and error pages |
| `runtime/host/` | Pinned `@deepseek-ai/dsh` manifest + pnpm layout (hoisted, multi-platform, peers installed) |
| `runtime/profile-trading/` | Profile seed: the manifests are generated by the build script from the workspace packages |
| `scripts/fetch-node.mjs` | Downloads + sha256-verifies the bundled Node distributions (`resources/runtime/node-<os>-<cpu>/`) |
| `scripts/stage-pnpm.mjs` | Installs the pinned pnpm into each staged Node distribution (per-platform bin shims), so the packaged app ships node + npm + pnpm |
| `scripts/verify-runtime-toolchain.mjs` | Release gate: node/npm/npx/pnpm must exist and run in every staged distribution for the current platform |
| `scripts/build-runtime.mjs` | Builds the workspace, packs every package, installs and stages the payload |
| `resources/` | App icons + generated runtime payload (git-ignored) |
| `mygo/` | mygo shell (migration target): Go module of the window, launcher, lifecycle, cookies, policy, recovery, profile seeding, cohort normalization and the agent channel |
| `scripts/stage-mygo-payload.mjs` | Stages the payload into `mygo/resources/runtime` with the per-platform node directory mapped to `runtime/node` |
| `scripts/build-mygo-mac.sh` | Packages the mygo shell for macOS: payload, `.app` + `.dmg`, signature check, notarization entry |
| `scripts/set-mygo-version.mjs` | Rewrites the mygo manifest's version from the release tag in the runner, so the mygo disk image and bundle version follow the tag as the Electron shell's do (`scripts/set-desktop-version.mjs`) |

The trading plugins are not published to npm, so `build-runtime.mjs` packs every workspace package into `runtime/profile-trading/vendor/` and wires the profile's direct dependencies and overrides to those tarballs. The generated profile manifest and lockfile are not committed; reproducibility comes from this repository's own versions.

## Build

### Prerequisites

The build machine needs Node 22+ and pnpm 11 (the repository toolchain). The packaged app itself needs nothing.

### Steps

```sh
cd desktop
npm install            # electron + electron-builder
npm run prepare-runtime  # fetch node dists + stage pnpm + build/pack/install/stage the payload
npm run dist:mac       # dist/*.dmg + *.zip (arm64 + x64)
npm run dist:win       # dist/*.exe (nsis) + *.zip (cross-build from macOS)
```

`npm start` runs the app unpackaged against the staged `resources/runtime/`, for development.

## Config

| Environment variable | Default | Meaning |
| --- | --- | --- |
| `DSH_HOME` | `~/.dsh` | Data home shared with the dsh CLI (config, sessions, keys). Set only for isolated testing. |
| `DSH_DESKTOP_NO_ATTACH` | unset | When set, skip the default-URL handoff check and always spawn a bundled host. |

The host version is pinned in `runtime/host/package.json`; the trading payload versions come from the workspace packages at build time. Both are recorded into `resources/runtime/VERSION.json`.

## Security model

- The dsh host binds loopback only (`127.0.0.1`); `--host 0.0.0.0` is rejected by the host itself.
- The window has no Node integration and a sandboxed preload; navigation is restricted to loopback (and the local splash/error pages), external links open in the system browser.
- The bundled Node distributions are verified against the release SHASUMS256.txt at build time.
- Trading safety semantics ship unchanged: dry-run default, explicit `liveTrading` switch, and the base approval gate stay in control of every order path.
- The app only ever writes under `$DSH_HOME` it resolved at startup, the Electron `logs` directory, and its own install location.

## Known limitations

- **Signing**: local macOS builds sign with the Apple Development identity auto-discovered in the keychain (`Identifier=com.dsh-trading.desktop`, team `3H4FK5CBYJ`) plus hardened runtime, so macOS privacy grants survive rebuilds. The grant itself is a manual step — add `/Applications/DSH Trading.app` under **System Settings → Privacy & Security → Accessibility / Screen Recording**; in embedded mode the driver never prompts. Development-signed builds are still rejected by Gatekeeper, so **release artifacts stay unsigned** until a Developer ID certificate plus notarization land. Downloading a release therefore still needs **System Settings → Privacy & Security → "Open Anyway"** (appears after the first blocked attempt) or `xattr -cr "/Applications/DSH Trading.app"`; Windows shows SmartScreen (More info → Run anyway). Pin a specific identity with `CSC_NAME=<cert SHA-1>`; a machine without any usable identity keeps producing the previous unsigned bundle and says so in a banner.
- **Windows arm64 and Linux** are not built; the runtime layout already covers adding them.
- First launch on a fresh machine spends a few seconds copying the preinstalled profile into `~/.dsh` (one-time).
- **Office skills and `load_workspace_dependencies` ship disabled.** The app never downloads or copies the primary-runtime payload (about 359MB). Before spawning the host it looks for `resources/runtime/primary-runtime`, then `$DSH_HOME/dsh-runtimes/dsh-primary-runtime`, and sets `DSH_PRIMARY_RUNTIME` only when the directory holds `runtime.json`; otherwise the two official rows stay explicitly disabled rather than falling back to a system Python. Place a compatible payload in either location (or export `DSH_PRIMARY_RUNTIME` yourself) to enable them. The host `~/.dsh` instance is deliberately never used.
- The bundled payload is built from the workspace checkout state; rebuild after pulling to carry connector or strategy updates into the installer.

## mygo shell (migration target)

`mygo/` is the mygo rewrite of this Electron shell: the window and its launcher, the single-instance lock, the attach handoff, the cookie prune, the page policy, the restart budget and the `window.desktop` bridge live in `mygo/internal/shell`, and the payload, packaging and agent-channel cards add profile seeding, cohort normalization, the primary-runtime gate, the macOS bundle and the automation client. Both shells ship side by side; the mygo shell keeps its own app name (`DSH Trading Mygo`), user data directory and bundle identifier, so the two never share a cookie jar or an instance lock.

### Payload

The payload is the one `prepare-runtime` stages for Electron, copied into the mygo project with the per-platform node directory mapped to `runtime/node`:

```sh
node scripts/stage-mygo-payload.mjs --platform darwin-arm64
# -> mygo/resources/runtime/{node,host,profile-trading,VERSION.json}
```

`mygo/resources/runtime/` is git-ignored (`mygo/.gitignore`): the node distribution, the host closure and the profile seed are build outputs, and the repository does not carry them. The script refuses an incomplete payload before a build starts (node/npm/npx, the host entry point, the seed's manifest and patch layer), and `--from` also accepts the runtime directory of an installed app (`/Applications/DSH Trading.app/Contents/Resources/runtime`), which is already in the mapped layout: that is how a Mac without the workspace stages the same payload.

At runtime the shell reads the payload in place (`mygo/internal/launch/runtime.go`): `runtime/node/bin/node`, `runtime/host/node_modules/@deepseek-ai/dsh/lib/bin.js`, `runtime/profile-trading` and `runtime/VERSION.json`.

### Profile, cohort and the primary runtime

- **Seeding** (`mygo/internal/profile`): a home without a profile gets the payload's seed; a profile this app seeded before is reseeded when the payload's identity (`VERSION.json`: node, host, profile hash) moved; a profile without the `.dsh-desktop-seed.json` marker is user-managed and never touched. On reseed the manifests and `node_modules` are replaced while the user's own `cordis.patch.yml` — and its backups — stay as they are.
- **Cohort** (`mygo/internal/cohort`): every `@deepseek-ai/*` copy the profile resolves is relinked onto the bundled host's copy, because two copies split module-level state and a preset then keeps its tools while losing its persona, its workspace `AGENTS.md` and its skill catalog. Packages the runtime does not ship, and package trees that belong to another install (a repo checkout, a pnpm store), are left alone.
- **Primary runtime** (`mygo/internal/launch/primary.go`): `DSH_PRIMARY_RUNTIME` is set only when a payload holding `runtime.json` exists at `resources/runtime/primary-runtime` or `$DSH_HOME/dsh-runtimes/dsh-primary-runtime`. Without one the shell logs `primary runtime: absent (Office skills and load_workspace_dependencies stay disabled)` and the host's two official rows stay disabled rather than falling back to a system Python. A `DSH_PRIMARY_RUNTIME` exported by the user passes through unchanged, and the host `~/.dsh` instance is deliberately never reached across.

### Build and sign

```sh
PATH=/path/to/go/bin:$PATH desktop/scripts/build-mygo-mac.sh        # ad-hoc signed .app + .dmg
PATH=/path/to/go/bin:$PATH desktop/scripts/build-mygo-mac.sh \
  --sign "Developer ID Application: Name (TEAM)" --notarize         # distribution
```

The script stages the payload (default source: the installed `/Applications/DSH Trading.app` runtime when it exists, else `desktop/resources/runtime`), builds the mygo CLI with Go when none is on `PATH`, runs `mygo build -platform darwin/arm64 -sign …`, then prints the bundle's `Info.plist`, the signature, the payload sizes inside the bundle and the artifact list. It needs macOS (`codesign`, `hdiutil`) and a Go toolchain: `mygo/go.mod` pins go 1.27.3 and `mygo build` compiles the app with it, so the packaging machine needs that version (`GOTOOLCHAIN=auto` fetches it).

Artifacts land in `mygo/build/darwin-arm64/`:

- `DSH Trading Mygo.app`: `CFBundleName` and `CFBundleDisplayName` are `DSH Trading Mygo`, `CFBundleIdentifier` is `com.dsh-trading.desktop.mygo` (a distinct bundle from the Electron app's `com.dsh-trading.desktop`, so both shells install and launch as themselves), `CFBundleShortVersionString` is the same `0.2.1` as `desktop/package.json`, and the icon is `desktop/resources/icon.png` (1024×1024, rendered into `AppIcon.icns`).
- `dsh-trading-desktop-0.2.1-arm64.dmg`: electron-builder's `dsh-trading-desktop-<version>-mac-<arch>.dmg` without the `-mac-` segment. `mygo build` names a disk image `<slug>-<version>-<arch>.dmg` with no platform word in it, so the slug carries the electron-builder prefix (`dsh-trading-desktop`) and the architecture stays; release tooling can glob `dsh-trading-desktop-*` and tell the shells apart by the `.app` and its `CFBundleIdentifier`.

Signing: the default is ad-hoc (`-sign -`), which `codesign --verify --deep --strict` accepts and Gatekeeper does not. Real distribution signing is the owner's step in a GUI login session: an ssh session's keychain is locked and `codesign` fails with `errSecInternalComponent`. `--sign "Developer ID Application: …"` signs with the identity mygo then also hardens and timestamps, and `--notarize` submits the `.dmg` with `notarytool --wait` and staples the app and the image (credentials from `APPLE_ID` + `APPLE_TEAM_ID` + `APPLE_APP_SPECIFIC_PASSWORD`, or `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER`). mygo's own route (`macos.signingIdentity` + `macos.notarize` in `mygo/mygo.json`) stays available; the committed configuration keeps the ad-hoc default so a machine without an identity still produces a runnable app.

Both forms are mygo's release build: `mygo build` sets `-X github.com/egoist/mygo.production=1`, so the window keeps developer tools off and the app is not a development bundle. The one switch for the inspector of native UI — and with it the automation plugin the agent channel drives — is the environment: `MYGO_INSPECTOR=1` keeps them (`github.com/egoist/mygo/cmd/mygo/build.go:448`, `:453`), anything else adds `-tags mygo_noinspector`. `-debug` keeps them too but drops the production flag, so a released app is never built with it. `--no-agent-channel` builds without them (see below); `--no-payload` builds with the payload already staged; `--skip-run-check` skips the launch that proves the channel is in — or out of — the artifact.

The script ends by proving what the build asked for. It reads the executable's own markers (the plugin's protocol code, or the stand-in's "this build leaves automation out"), then opens the built app once with `MYGO_AUTOMATION` set and a throwaway `DSH_HOME` under the temp directory and asks `agentctl windows` for the window list, retrying briefly because the window opens a moment after the app is ready — a build without the channel is proved by the app's own line on stderr. Where the app cannot be launched here — no GUI session, or no Go to build `agentctl` — the script falls back to the markers alone and says which check it could not run.

### Release pipeline: telling the two shells' artifacts apart

`.github/workflows/desktop-release.yml` packs both shells from one tag. `build-desktop` (matrix `macos-latest` / `windows-latest`) keeps producing the Electron installers, and `build-desktop-mygo` (`macos-latest`, arm64 only) produces the mygo `.app` and `.dmg`. The mygo job generates the payload in the job — CI has no `/Applications/DSH Trading.app` to copy it from — with `fetch-node.mjs` → `stage-pnpm.mjs` → `build-runtime.mjs`, maps it with `stage-mygo-payload.mjs --platform darwin-arm64`, and packages it with `build-mygo-mac.sh --no-payload`. It repeats install and build, but not the tests the release already runs on the same commit — `pnpm test:desktop` and the whole `pnpm -r test` are the gate of `npm-publish` and `build-desktop`, and no Release is created unless all three jobs pass.

The file names do not separate the shells: the mygo disk image is `dsh-trading-desktop-<version>-arm64.dmg` and the Electron one `dsh-trading-desktop-<version>-mac-<arch>.dmg`, so `-mac-` is the only difference and nothing may key off the name. What separates them:

| | Electron | mygo |
| --- | --- | --- |
| workflow job | `build-desktop` (macOS + Windows matrix) | `build-desktop-mygo` (macOS) |
| Actions artifact | `desktop-mac` / `desktop-win` | `desktop-mac-mygo` (`.dmg`) and `mygo-app-bundle` (`.app`) |
| `CFBundleIdentifier` | `com.dsh-trading.desktop` | `com.dsh-trading.desktop.mygo` |
| Release assets | dmg + zip per arch, Windows NSIS exe + zip | the arm64 `.dmg` |

`github-release` downloads only artifacts matching `desktop-*` into `dist/`, hashes that directory and uploads it, so the mygo `.dmg` travels with the Electron files through the same `SHA256SUMS.txt`. The mygo `.app` is deliberately named without that prefix: a bundle is a directory, `sha256sum ./*` and `gh release create dist/*` take files, and a directory in `dist/` would break both.

The mygo artifact is ad-hoc signed unless the repository holds the optional secrets: `--sign` is passed only when `MYGO_SIGN_IDENTITY` exists, and `--notarize` only when `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_SPECIFIC_PASSWORD` are all set; the packaging step prints which mode it used. No secret is required, and a Developer ID build additionally needs the certificate in the runner's keychain, which this workflow does not import. The mygo version follows the tag like the Electron one: `mygo.json` carries the committed version and the job rewrites it in the runner with `set-mygo-version.mjs` (the counterpart of `scripts/set-desktop-version.mjs`), so `CFBundleShortVersionString` and the disk image name match the Release.

The only trigger is a `v*` tag push: a PR or a push to main does not run this workflow, so the mygo job cannot be proven locally and its first real execution is a tag push. What a local machine can check is the workflow (YAML parse, `actionlint`, `pnpm ci-wiring:check`) and the command sequence up to the macOS-only steps; the run's log then carries the payload sizes, the signature, the artifact names and the agent-channel verdict `build-mygo-mac.sh` prints.

### Agent channel

The released app carries the automation plugin the shell imports (`mygo/automation.go`), because the agent channel is how a build is accepted and driven: `build-mygo-mac.sh` exports `MYGO_INSPECTOR=1` unless `--no-agent-channel` is given, mygo then leaves out `-tags mygo_noinspector`, and the plugin's `init` listens on the Unix socket `MYGO_AUTOMATION` names. Without that variable the plugin does nothing at all. A build that passes the tag instead compiles the plugin's `off.go` stand-in: nothing listens, and an app started with `MYGO_AUTOMATION` says on stderr that the channel is not in this build.

`mygo/cmd/agentctl` is the local client (build it for the Mac with `CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -o agentctl ./cmd/agentctl`):

```sh
MYGO_AUTOMATION=/tmp/dsh-mygo.sock \
  "mygo/build/darwin-arm64/DSH Trading Mygo.app/Contents/MacOS/DSH Trading Mygo" &

agentctl windows                      # the app's windows, as JSON
agentctl eval 'document.title'        # a script in the page, its JSON value back
agentctl capture /tmp/window.png      # the window as a PNG
agentctl idle 5s                      # wait until the window settles
```

- `windows` lists id, title, kind, url, bounds, focus and visibility. This shell's window is `kind: "page"`.
- `eval <script>` evaluates the script in the page and prints the JSON value; `-window <id>` addresses a window other than the focused one.
- `capture <file>` writes the window as a PNG without Screen Recording permission (the app renders its own window) and prints the byte and pixel size.
- `idle [timeout]` waits until the window settles.

**A page window has no accessibility tree.** The shell's window shows the GUI's web page, so `tree` answers `unsupported` ("window 7 shows a web page: use eval") and `act`/`input` only apply to windows of native UI. Everything the page shows is reachable through `eval` — `document.querySelector`, `getComputedStyle`, any `window.__x` the page set — and that is what the acceptance runs assert against. Use `capture` when the question is what the window looks like, and `eval` when it is what the page says.

#### What shipping the channel costs

The tag that keeps the inspector also compiles in the automation plugin, so both travel to the user:

- The socket exists only when the app is started with `MYGO_AUTOMATION` naming a path, and the plugin creates it mode `0600` after tightening the umask (`github.com/egoist/mygo/plugins/automation/listen_unix.go`): only the user who launched the app can open it. Nothing listens in an ordinary double-click launch.
- Whoever can open it sees what the window shows and acts on it: window geometry, a PNG capture, and `eval` in the GUI page, which reaches everything the page can — including the `window.desktop` bridge the page already calls. There is no elevation and no path into `$DSH_HOME` beyond what the page has.
- The inspector of native UI adds about 250 KB to the binary. This shell's window keeps web developer tools off in a production build (`PageOptions.DevTools` stays `DevToolsAuto`, which is off once `production=1`), so the panel is not a way in here; the plugin is the part that answers.

That is accepted because the acceptance runs drive the installed app: `windows`/`eval`/`capture`/`idle` against the artifact under test is the only end-to-end check that the shipped build works, and a separate debug-flavoured build would verify a binary nobody runs. It is a local surface on the user's own machine, gated by the user's own environment.

`--no-agent-channel` builds the release without either: mygo then passes `-tags mygo_noinspector`, the stand-in stands in, and the artifact answers nothing on the socket. Use it for an artifact that must carry no local driver at all — a copy handed to someone who is not the operator, or a distribution where the extra surface is not wanted — at the price of losing the run-based acceptance (the script still proves the absence by launching the app and reading the stand-in's line, or, without a GUI session, by the binary's markers).
