# 自持契约包：id 冻结面、版本协商、scope 三平面

日期：2026-10-01 · 阶段：P4 步骤 1 · 卡片：bf92b5d2 · 包：`@dshtrading/contract`（零第三方依赖）

## 事实

- **自持而不是复用官方 Typert wire**（卡片裁决）：移动端的信任面是"设备 + 可撤销令牌"，而 Typert 的信任面是同源浏览器会话（无法按设备撤销）；把 App 发布节奏绑到 DSH cohort 上也会让"官方升级"与"App 能用"变成同一件事。
- **id 冻结面**（ids.ts）：`clientRequestId` 可见（幂等键，客户端要能带它重试）；**`clientOrderId` 永不可见** —— 它能被用来绕开核心直接对 venue 讲话（很多交易所支持按它撤单/查询），一旦下发，执行核的限额/mandate/风险闸门就都建立在"只有核心能对 venue 讲话"之上的假设就破了；`orderId = ord_ + UUID` **只比较不解析**、一律 factory 生成；`venueOrderId` 只是字段、永不作句柄。
- **唯一下发路径**：`toClientOrderView()` 是唯一把内部订单投影给客户端的函数（`clientOrderId` 在这里被丢掉，想加回来必须改它，而不是某个调用点顺手带上）；`assertNoClientOrderId()` 做下发前最后一道闸，递归抓任意层级的夹带（含数组）。
- **版本策略**（version.ts）：major 进 URL；minor 只增不减；`X-Dsht-Caps` 求交集；缺必填能力或超出 **N-2** 窗口 ⇒ `426 CLIENT_TOO_OLD`（明确要求升级，而不是静默降级成残缺渲染）；比服务端新 ⇒ `CLIENT_TOO_NEW`。
- **scope 三平面**（scopes.ts）：`grantableByDefault()` 无论请求怎么写都剔除 `control`；输出按声明顺序（稳定顺序是契约的一部分）。

## CI 门禁：`pnpm contract-id:check`

`scripts/contract-id-gate.mjs` 扫描全仓源码，禁止出现匹配 `ord_[0-9a-f]{8}-[0-9a-f]{4}-4` 的**写死字面量**。理由：契约是"只比较不解析"，一旦某处写死或解析，它就获得了语义，接着有人依赖这个语义——改格式就成破坏性变更。例外只有两处：契约包的 factory/正则自身，以及测试里带 `id-gate-allow` 标注的故意样本。

**门禁的自测放在契约包里**（`packages/contract/test/id-gate.test.ts`）而不是 `scripts/`：伪造样本与它的标注规则放在同一个包里，规则才不容易被绕过；样本本身用**运行期拼接**构造，于是门禁扫自身测试文件时不会误报（这条是被门禁自己抓出来的——第一版把字面量直接写在测试里，门禁准确地把测试文件报成了违规）。

## 测试（15 例全绿）

orderId 形态与"只比较不解析"（无 venue slug、前缀后就是 UUID）、`isOrderId` 拒绝四种伪形态、投影后无 `clientOrderId` 且有 `clientRequestId`、`assertNoClientOrderId` 抓嵌套/数组并指出路径、协商放行与交集、缺能力/超 N-2/过新三种 426、N-2 窗口内放行、caps 头解析往返稳定、control 永不默认签发、`isScopePlane` 只认三平面；外加门禁四条自测。纯函数，无 mock 无 sleep。


## 移动端的契约面：推送通知载荷（P4 步骤 4 前置，同日补）

P4 步骤 4（移动 App）在开工前卡在一件需要人决定的事上：**内部分发方式**（EAS / 本地构建 / 企业签名，涉及外部账号与证书）。但这条卡片里有一块**与分发方式无关**的部分可以先落地 —— 卡片对通知的要求是"携带类型 / 严重度 / deskId / 深链 / 倒计时 / 可用动作"，那是一个**契约**，不是某一种打包方式的产物。

`packages/contract/src/push.ts` 三条立场：

1. **封闭枚举**（severity 三档、kind 五类、actions 五种）：推送是最容易被"顺手加个字段"的通道，而通知上的**可用动作决定了用户点一下会发生什么** —— 它必须可校验，不能自由发挥。
2. **倒计时只表达"还剩多久"，不表达"到点自动做什么"**：动作永远由人按下确认。通知里带"自动执行"语义等于**把授权放进推送通道**。
3. **深链只允许 `/` 前缀**：允许 http(s) 等于允许推送服务把用户送去任意站点 —— 推送通道的信任级别不该那么高。

另有一条来自风险语义的硬规则：**critical 通知必须至少给一个可用动作** —— 只喊危险而不给出口，等于把人钉在原地。静音同理：`shouldInterrupt` 只挡非 critical，**静音不是关闭风险的开关**。

测试 7 例：合法载荷 + 三个枚举的封闭性；未知 kind/severity/action 拒绝；http 深链拒绝；critical 无动作拒绝；倒计时四种非法值拒绝；fallbackText/动作上限/revision/deskId 四种越界拒绝；静音只挡非 critical。

**未验证**：`fallbackText` 的 180 字符上限是**设计值**（未按真实通知折叠行为标定）；APNs/FCM 的实际载荷尺寸限制（iOS 4KB / Android 4KB）未核对；生物识别与设备配对的服务端交互未做（配对与 `grantControl` 已存在于 edge，但移动端调用路径未写）。


## 确认策略进契约（P4 步骤 4 契约面，同日补）

卡片要求移动端"生物识别确认（控制与审批类）"。这里的**机制**两端不同（网页用 `window.confirm`、移动端用生物识别），但**判据必须只有一个家** —— 否则会出现"网页拦住了、手机没拦"或反过来，而这种不一致恰好出现在最危险的动作上。

`packages/contract/src/confirm.ts` 三档：`none`（只读：ack/dismiss/open-detail/retry-sync）、`confirm`、`biometric`（审批类 approve/reject 与**全部控制类**）。

**一条不许妥协的不变量**：**control 平面上的任何动作都不得低于 `biometric`** —— kill/flatten 会让真实仓位动起来，把它们降级成"点一下就行"是事故的常见起点。这条以 `auditConfirmPolicy()` 的形式**可机检**（表与 `ACTION_KINDS` 对不上、或任一 control 动作低于 biometric 就红）。

**网页端不假装有生物识别**：`requiresBiometric` 对 web 端一律返回 false，界面据此显示"此动作在移动端需生物识别"，而不是假装验过了。

另加一条**跨包一致性断言**（cockpit 测试）：驾驶舱控制面的四个动作在契约里必须都是 `biometric` —— 有人把契约降级而界面照旧渲染，这条会红。

测试 4 例（契约）+ 1 例（cockpit 一致性）：策略表自检通过且覆盖全部动作；三档分派正确；网页端不假装有生物识别；**把 kill 降级会让自检变红**（证明不变量不是摆设）。契约包累计 41 例。


## 离线快照、陈旧度与深链（P4 步骤 4 契约面最后一块，同日补）

`packages/contract/src/offline.ts` 三条立场：

1. **过期数据不渲染数据本身**：过了 `ttlMs` 只显示"本地数据已过期（N 秒前），请联网获取后再操作"，**不显示那份数据**。理由：交易界面上的旧持仓会被当成现状 —— **显示一个可能完全错的持仓，比什么都不显示危险得多**。测试专门断言过期视图的 JSON 里**不含数据内容**。
2. **无数据 ≠ 空数据**：`stalenessOf(undefined, …)` 是 `unknown`、与"取到了空列表（fresh）"区分开。两者在界面上是完全不同的两句话。
3. **深链是封闭集合**：只认 `escalations / decisions / positions / control` 四个目标；外部 scheme、未知目标、空目标一律拒绝（**不"尽力跳转"**）。id 做 URL 解码，不原样当路径用。

另有一条防御性设计：`budgets` 自相矛盾（fresh > stale）时一律判 `unknown` 并给"请联网"提示，**不猜一个档位** —— 配置写错时宁可什么都不显示。

测试 7 例：unknown 与空列表的区分；四档边界；矛盾边界判 unknown；**过期视图不含数据内容**；三档徽标强度递增；深链五种输入（两个合法、外部 scheme、未知目标、空目标）；id 解码。契约包累计 **48 例**。


## 数据源守卫（P4 步骤 5 的契约层，2026-10-01 补）

卡片原文（步骤 5）的硬约束是：**「同一份 `$DSH_HOME` 同一时刻只允许一个 dsh host 写者；两种形态下不得混显两个数据源（数据源是会话级单例、每条数据带 `sourceId`、渲染层拒绝跨源显示、切换期只读 + 双源对账）」**，证据要"契约测试（同 id 不同 sourceId 只显示当前源）+ 一次切换演练记录（含回滚点）"。

`packages/contract/src/source-guard.ts` 把这条硬约束做成**可执行判定**（不碰渲染与网络）：

- `viewOf(data)`：渲染层的唯一入口，只返回当前源的数据 —— **同 id 出现在两个源时，另一个源那条根本不在视图里**（不是"被过滤后解释一下"，而是不存在）；
- `switchTo(next)`：立刻进入只读；`writable()` 变 false —— **"切换期只读"若靠调用方自觉，就一定会在某条路径上漏掉**；
- `reconcile(active, incoming)`：条数一致才结束只读并换源；不一致则**保持只读 + 给出原因**（宁可停在只读，也不要把半个源显示出来 —— 静默"假装对上了"是这类切换最危险的失败方式）；
- 切到同一个源不算切换（刷新不该把界面变成只读）。

**契约测试 4 例**覆盖上述四条（卡片点名的那条在第一个用例：同 id 不同 sourceId ⇒ 视图只有当前源）。

**仍未做（⑤ 的其余部分）**：桌面壳 handoff 扩展到远端 bot URL（还没定位到现有 handoff 代码的位置）；切换演练记录含回滚点。

## 未验证项（如实标注）

- **HTTP/WS 传输层未实现**：本步只落地契约的数据面（id/版本/scope 与门禁），一元写、WS 单向下行、journal 游标补页的**服务端实现**属后续步骤。
- **与 P2 edge 的 scope 词汇尚未合并**：两处各有一份 `read/command/control`（契约包是线上面权威、tradectl/edge 是执行面实现）。合并需要跨包改造，**另开一次变更**；在那之前两边若漂移，只能靠 review 发现——已记为待办。
- **N-2 兼容只有单元断言**，没有真实旧客户端的联调证据。

## 被否决的方案

- **复用官方 Typert wire**：见事实第一条（信任面与发布节奏两条都不成立）。
- **把 `clientOrderId` 一并下发**：等于给客户端一把绕开核心的钥匙。
- **从 `orderId` 里编码信息**（如 venue 前缀）：那会让"只比较"变成"可解析"，格式从此不能改。
- **缺能力时静默降级渲染**：客户端会看到一个残缺但"看起来正常"的界面——426 明确要求升级更诚实。
