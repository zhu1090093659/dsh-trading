# Agent Note: 看盘 UI 二期 #36-#41 分工落定，任务交付改走分支+PR 流

Archived: 2026-09-04
Status: implemented

## Problem

2026-09-02 协作者 Aa728848 一次性提交六项看盘功能 Issue（#36-#41），当时无人分配、
未做事实核对，直接开工会在 MarketDataService 契约与加密连接器等共享文件上互相踩踏；
同时本仓沿用「owner/collaborator 直推集成分支」的交付惯例，多线并行时直推 main
容易积累大冲突，回滚粒度也差。

## Decision

- 建聚合跟踪 Issue [#42](https://github.com/zhu1090093659/dsh-trading/issues/42)
  （任务清单 + 分工 + 流程约定 + 开工前事实核对），#36-#41 以任务列表关联挂靠；
  六个 Issue 均已分配并留言。
- 分工按文件重叠度切两条线：UI 线 #36 #37 #41 → Aa728848；数据线 #38 #39 #40 →
  zhu1090093659（owner）。#36 的三大报表数据端点依赖数据线补齐，UI 骨架用现有
  单期 `getFundamentals` 先行，不被阻塞。
- **交付流改为分支+PR**（owner 2026-09-02 指示）：每个任务从最新 main 开独立分支
  （`feat/<issue号>-<短名>`），走 PR 合并回 main，PR 描述挂对应 Issue；至少一个
  审查批准。本仓此前的直推交付惯例就此废止。
- 同线共享文件的任务串行：数据线 #38 → #39。
- 留言同时落库开工前事实核对：#37 四 kit `news.ts` 已就绪（最小切口，建议先做）；
  #38 仅 connector-okx 有 funding/OI 实现，binance/bybit 需先扩连接器且契约无衍生品
  方法；#39 `getOrderbook` 不在契约（packages/api/src/index.ts:207-238）；#40 闸门
  设施齐全，前端手动下单不得旁路 dry-run+审批闸门；#41 回测引擎与知识库存储均在，
  需确认回测输出带逐笔时间戳。

## Alternatives considered

- **维持直推集成分支**：落选——六条线并行、#38/#39 与既有契约/连接器文件高度重叠，
  直推把冲突积累到 main，且单提交回滚困难。
- **单条集成分支串全部任务**：落选——等价于把六条线捆成一次发布，任一线卡住全体阻塞。
- **六个 Issue 全部分配给 Aa728848、owner 只审查**：落选——#40 触实盘安全闸门，
  数据线（含 #40）由 owner 亲自持有更稳；协作者把 UI 规格写得最细，UI 线归他。

## Consequences

- 本仓后续一切功能任务默认走「新分支 + PR 合并 main」，不再直推；PR 合并需至少
  一个批准，#40 合并前必须真实链路验证（dry-run 优先）。
- #42 成为该批次唯一进度入口，子 Issue 完成即勾选其任务清单。
- 事实核对结论（okx-only 衍生品数据、契约缺 `getOrderbook` 等）已随 Issue 留言落库，
  开工前不需重复调研。
